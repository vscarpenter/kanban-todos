01 — Executive Summary

Health verdict

8.0 /10
Overall Health

Mature, disciplined codebase. Two specific gaps to close in the next sprint.

Kanban Todos is a well-engineered client-side application with strong type discipline, comprehensive ADRs, clean security baseline, and a passing test suite (492/492). The standards bar set in coding-standards.md v14.0 is largely met. The most consequential remaining gaps are operational rather than structural: no React error boundary at the application root means an unhandled render error blanks the UI, and the store initialization error path swallows failures by setting isInitialized regardless of outcome. Both are small fixes with disproportionate impact on user-visible reliability.

Coverage sits at 61.46% lines, well above the configured baseline (37%) but below the standards target (80%). The shortfall concentrates in three specific surfaces — guideSteps.tsx (0%, 477 lines), the wizard step components under components/import/, and several Radix-wrapped UI primitives — rather than being broadly distributed, which makes it tractable.

Top 5 risks

  1. No app-level error boundary. A render error in any component crashes the UI to a blank page. See finding
  2. Init errors are swallowed. KanbanBoard.tsx:63-65 sets isInitialized=true in both success and catch branches, hiding DB failures. See finding
  3. JSON import lacks prototype-pollution guard. fileHandling.ts:78 uses JSON.parse without a reviver to reject __proto__/constructor keys. See finding
  4. Logger underused. A structured logger exists at lib/utils/logger.ts but 31 raw console.* sites bypass it, fragmenting observability. See finding
  5. IndexedDB has no migration path. DB_VERSION = 1 is hardcoded; onupgradeneeded only creates missing stores. A future schema change has no safe rollout. See finding

Top 3 strengths

  1. Type discipline is exemplary. Zero any, zero @ts-ignore, zero non-null assertions in production code; strict mode enabled.
  2. Security baseline is comprehensive. bun audit clean, CSP with frame-ancestors 'none' + HSTS + Permissions-Policy, ESLint react/no-danger: error, RFC-4122 UUID validation, crypto.randomUUID for IDs, rate limiter on search.
  3. Process artifacts are present and current. 5 ADRs covering every major hard-to-reverse decision, tasks/todo.md + tasks/lessons.md in place, 100% conventional-commit compliance over the last 30 commits, zero TODOs/FIXMEs across 169 source files.

Top 3 priorities — next sprint

  1. Add ErrorBoundary at the app root and fix the init catch-and-mask in KanbanBoard. Both are small, both ship reliability. ~1 day
  2. Add a JSON.parse reviver in fileHandling.readJsonFile that rejects prototype keys and SVG/event-handler patterns before schema validation runs. ~½ day
  3. Migrate the 31 production console.* calls to logger and raise the vitest coverage thresholds from baseline (37%) toward the actual measured floor (60%) so regressions are caught. ~1 day

03 — Dimension

Standards compliance

Source of truth: coding-standards.md v14.0 · 0 Critical · 0 High · 2 Medium · 3 Low

The codebase honours the spirit and most of the letter of its own standards. Function-length and nesting limits are respected; the few outliers are JSX-heavy render bodies that are linear, not deeply nested. Files over 350 lines are largely justified by single-responsibility cohesion (validators, security utilities, filter logic). Three readability concerns remain, all small.

Two dialog components exceed the file-size guideline MediumHigh confidenceSmall

src/components/TaskDialog.tsx · 408 lines

src/components/ExportDialog.tsx · 409 lines

Both render large monolithic forms with mixed state, side effects, and UI. The standards target is ~350-400 lines split by responsibility. TaskDialog's form fields (title, description, tags, schedule) are natural extraction boundaries; ExportDialog can split into <ExportOptions> (the control surface) and <ValidationResults> (the results pane).

Recommendation

Extract one cohesive sub-component per dialog. Do not introduce abstraction layers — direct component decomposition only, per YAGNI.

Effort

Small (1 day, both dialogs together).

Magic number for file-size limit MediumHigh confidenceSmall

src/lib/utils/security.ts:203

The import file-size check uses an inline literal: const maxSize = 10 * 1024 * 1024;. The rest of security.ts uses named constants (INPUT_LIMITS, RATE_LIMIT_CONFIG), so this is an inconsistency rather than a pattern violation.

Recommendation

const MAX_IMPORT_FILE_SIZE_BYTES = 10 * 1024 * 1024; // 10 MB
31 console.* sites bypass the structured logger LowHigh confidenceSmall

A well-designed logger lives at src/lib/utils/logger.ts (SSR-guarded, JSON output in production, plain console in dev), but only ~5 modules call it. Components and stores still write to console.error directly. next.config.ts strips console.* from the production bundle, so this is a development-experience and observability concern rather than a leak.

Examples

src/components/KanbanBoard.tsx:63 — console.error('Failed to initialize stores:', error)

src/components/PwaUpdater.tsx:56,69,88 — three different SW failure modes, no structured context

src/components/ExportDialog.tsx:161 — console.error('Export failed:', error)

Recommendation

Migrate to logger.error(message, { context }). Once the migration is complete, add an ESLint rule banning bare console calls outside logger.ts.

Test naming leans imperative rather than behavioural LowHigh confidenceMedium

~17% of test descriptions use the standards-preferred should_X_when_Y form (e.g. "should disable up button for first board"). The remaining 83% use "renders …", "applies …", "handles …". The tests themselves assert behaviour, so this is a stylistic gap rather than a quality defect.

Recommendation

Renaming is invasive (34 files) for limited payoff. Defer unless you adopt a snapshot-style report that benefits from sentence-form test names. Note in coding-standards.md that "renders X" is an acceptable shorthand for component tests.

No commented-out code; no any; no escape hatches Strength

Audit returned zero matches for: multi-line commented code blocks, any outside tests, @ts-ignore, @ts-expect-error, non-null assertions ! in production. Six as unknown as casts exist in conflictMerge.ts (lines 123, 132, 136, 151, 155, 171) — they bridge typed entities and a generic record-based merger. They are not justified by inline comment; the standards require one.

Recommendation

Add a single block comment at the top of conflictMerge.ts explaining the cast pattern, or wrap the conversions in a typed helper like function asRecord<T>(x: T): Record<string, unknown> { return x as unknown as Record<string, unknown>; } with one comment at the helper.

04 — Dimension

Test quality & coverage

0 Critical · 1 High · 3 Medium · 1 Low · 492/492 passing

The test infrastructure is solid: vitest + jsdom + @testing-library/react + fake-indexeddb for unit/integration, Playwright for end-to-end. The full suite passes in 3.5 seconds. Strengths concentrate at the boundaries: database.test.ts uses fake-indexeddb against the real TaskDatabase class (correct boundary testing), and the 11 Playwright suites cover every golden path. Weaknesses concentrate in the middle: store tests reach for setState() to set up preconditions instead of using the actions themselves, and three large surfaces (guideSteps, ExportDialog, the import wizard steps) sit at 0% coverage.

Store tests mutate state directly with setState() inside test bodies HighHigh confidenceMedium

src/lib/stores/__tests__/taskStore.test.ts — multiple sites (e.g. 146, 194, 212)

src/lib/stores/__tests__/boardStore.test.ts — similar pattern

The standards-preferred pattern is: arrange state by calling the store's public actions, act by calling the action under test, assert against the resulting state. These tests bypass the actions, reaching into useStore.setState() to seed fixtures mid-test. This is brittle (renames break tests), couples tests to internal shape, and produces tests that pass even when the action paths regress. Combined with the global database mock in src/test/setup.ts:68-70, the store layer is largely tested in isolation from the persistence layer it exists to coordinate.

Recommendation

(1) Remove the global database mock in src/test/setup.ts and let store tests use fake-indexeddb like database.test.ts does. (2) Replace mid-test setState calls with action-based setup. (3) Add a contract-level test per action: "after addTask, the task is reachable via filteredTasks and persisted in IndexedDB".

guideSteps.tsx (477 lines) has zero test coverage MediumHigh confidenceMedium

src/components/userGuide/guideSteps.tsx

The file is largely a data structure (array of step objects with embedded JSX), which is why its risk is mitigated — there is little branching logic to break. The risk is regression on rendering: a malformed JSX node or missing key would surface only at runtime in the guide dialog, a low-traffic path.

Recommendation

Add a smoke test that renders each step's JSX and asserts the heading and primary copy. Even a 5-test snapshot would close the regression window. Treat coverage on this file as nice-to-have, not blocking.

taskStore.import.test.ts covers only 2 cases for a critical path MediumHigh confidenceMedium

src/lib/stores/__tests__/taskStore.import.test.ts

Import is one of two paths where user-controlled JSON enters the system (the other being export round-trip), and the existing security audit identified prototype-pollution as the main gap there. Two tests is not enough surface to catch regressions in conflict resolution, version mismatch, partial imports, or malformed data.

Recommendation

Add tests for: (a) duplicate-ID merge strategies, (b) version mismatch handling, (c) JSON containing __proto__ keys (should reject after Medium-severity fix lands), (d) partial-import error reporting, (e) round-trip equality.

crypto.randomUUID is globally mocked to a fixed value MediumHigh confidenceSmall

src/test/setup.ts:40-45

Every test sees the same UUID. This makes "two distinct entities have distinct IDs" untestable and lets bugs that rely on ID collisions slip through.

Recommendation

Either return a monotonic counter UUID from the global mock or remove the global mock entirely and let tests that need a stable ID use vi.spyOn(crypto, 'randomUUID') locally.

Coverage thresholds set at the baseline floor MediumHigh confidenceSmall

vitest.config.ts:30-35

Thresholds are configured at 37% / 38% / 35% / 36% labelled "baseline thresholds as of initial compliance pass (raise over time toward 80%)". Actual measured coverage is 61.5% / 57.9% / 54.3% / 61.5%. The threshold is now a ceiling on regression, not a floor.

Recommendation

Raise thresholds to within ~2 points of the current measured values (e.g. 59 / 55 / 52 / 59). Re-tighten after each coverage push.

A few component tests assert on DOM tagName / class — brittle to markup changes LowMedium confidenceSmall

src/components/__tests__/BoardView.integration.test.tsx:164-169

Asserting el.tagName === 'H1' couples tests to the heading level chosen at write time. Re-leveling a heading for a11y or layout becomes a test failure unrelated to behaviour.

Recommendation

Prefer screen.getByRole('heading', { level: 1 }) or query by accessible name. The Testing Library API discourages tagName/class assertions for exactly this reason.

05 — Dimension

Security & supply chain

0 Critical · 0 High · 2 Medium · 0 Low · OWASP-relevant

This is a client-only static-export PWA with no backend, so the OWASP Top 10 surface is narrow: XSS via untrusted strings, malicious file imports, supply chain on the dependency tree, and missing security headers in transit. Defences are well-layered. React auto-escaping is the primary XSS control, backed by the ESLint react/no-danger: error rule that forbids the only unsafe-HTML escape hatch, and CSP delivered via the CloudFront response-headers policy. bun audit reports zero advisories. Two specific gaps remain in the import path.

JSON import is not guarded against prototype pollution MediumHigh confidenceSmall

src/lib/utils/fileHandling.ts:78 — jsonData = JSON.parse(fileContent)

A malicious import file containing "__proto__": { "polluted": true } or "constructor": { "prototype": … } reaches JSON.parse unfiltered. Downstream schema validation and sanitizeData() (when called with removeInvalidFields: true) strip unknown fields, but prototype-chain mutation can occur during the parse itself in some engines, and not all import paths set the strict sanitization flag.

Recommendation

jsonData = JSON.parse(fileContent, (key, value) => {
  if (key === '__proto__' || key === 'constructor' || key === 'prototype') {
    throw new Error('Invalid property name in import');
  }
  return value;
});

Optionally extend the reviver to reject strings containing <, javascript:, or on\w+= patterns as defence-in-depth even though React escaping protects the render path. Pair with a test in taskStore.import.test.ts that asserts rejection.

No JSON size check after parse — only file-size check before MediumMedium confidenceSmall

src/lib/utils/fileHandling.ts (file size limit: 10 MB upfront)

A deeply-nested JSON file under the 10 MB byte threshold can still expand to a much larger in-memory structure and either OOM the browser tab or stall validation. The 10 MB pre-parse limit is reasonable; the practical risk is low for a personal-data PWA.

Recommendation

Add a post-parse depth check (e.g. reject nesting deeper than 16 levels) and a count check (e.g. reject >10,000 tasks or >500 boards). Both are O(1) to add and bound the worst case.

CSP, transport, and content-type headers — all present and verified Strength

docs/security-headers-baseline.json + scripts/test-security-headers.sh

The CSP is enforced via CloudFront response-headers policy and includes:

default-src 'self'
script-src 'self' 'unsafe-inline'   # Next.js anti-FOUC + RSC hydration
style-src 'self' 'unsafe-inline'
img-src 'self' data: blob:
connect-src 'self'
object-src 'none'
base-uri 'self'
form-action 'self'
frame-ancestors 'none'              # clickjacking defence
worker-src 'self'                   # PWA service worker
upgrade-insecure-requests

Plus Strict-Transport-Security: max-age=31536000; includeSubDomains, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, and a tight Permissions-Policy denying camera/microphone/geolocation/payment/usb/sensors. 'unsafe-inline' on script/style is the standard Next.js static-export trade-off; the baseline JSON acknowledges it as follow-up tech debt.

No secrets, strict UUID validation, crypto.randomUUID for IDs Strength

Repo-wide grep for password, api_key, secret, token, AWS access-key patterns returned only documentation references — no real values. .env.example is a documentation file. UUID validation in security.ts uses RFC 4122 regex (version bits, variant bits enforced). IDs are generated by crypto.randomUUID(), not Math.random().

Search rate-limited to defeat regex CPU exhaustion Strength

src/lib/utils/security.ts:270-309 + applied at taskStore.filters.ts:182

A sliding-window rate limiter caps search to 10 requests per 1000 ms. This is appropriate for a client-only PWA where the threat is "search query that triggers an expensive linear scan over many tasks", not network-level DoS.

06 — Dimension

Architecture, coupling & cohesion

0 Critical · 0 High · 3 Medium · 1 Low

The architecture is conventional and clean: three Zustand stores (board, task, settings) over a singleton TaskDatabase that wraps IndexedDB. There are no circular dependencies, the tasks/boards/settings/archive object stores are independently indexed, and Components import from stores via the standard Zustand hook pattern. Five ADRs in docs/adr/ document every major hard-to-reverse decision (IndexedDB, Zustand, static export, Tailwind+shadcn, dnd-kit). The store layer is split into action files (taskStore.crudActions, taskStore.filters, taskStore.import) which keeps individual modules at a tractable size.

IndexedDB has no migration strategy beyond v1 MediumHigh confidenceMedium

src/lib/utils/database.ts:4 — DB_VERSION = 1

The onupgradeneeded handler only creates object stores if they're missing. Any future schema change — adding an index, renaming a field, splitting a store — requires bumping the version, but there is no scaffolding for the migration callback. The first schema change will need to write the migration plumbing under deadline, which is the wrong time.

Recommendation

const MIGRATIONS = [
  // v1 → v2 example
  (db: IDBDatabase, tx: IDBTransaction) => {
    const store = tx.objectStore('tasks');
    if (!store.indexNames.contains('priority')) store.createIndex('priority', 'priority');
  },
];
request.onupgradeneeded = (event) => {
  const oldVersion = event.oldVersion;
  const tx = request.transaction!;
  for (let v = oldVersion; v < DB_VERSION; v++) MIGRATIONS[v]?.(request.result, tx);
};

Write an ADR (0006-indexeddb-migrations.md) describing the versioning policy.

boardStore mixes sanitization with state mutation MediumHigh confidenceSmall

src/lib/stores/boardStore.ts:179-211 (updateBoard)

The store calls sanitizeBoardData() inline before persisting. The store should be a thin coordinator between actions and persistence; sanitization belongs in a validation layer the action calls into. This is a small SRP violation, mitigated by the fact that the sanitization is short and clearly delineated.

Recommendation

Extract sanitizeBoardUpdates(existing, updates) into lib/utils/boardHelpers.ts and have the store call it directly. The store keeps the responsibility of "thin coordinator" intact.

Six as unknown as casts in conflictMerge lack justification comments MediumHigh confidenceSmall

src/lib/utils/conflictMerge.ts:123, 132, 136, 151, 155, 171

The casts bridge typed entities (Board, Task, Settings) and an internal Record<string, unknown>-based generic merger. The pattern is defensible — a strictly-typed merger would either lose ergonomics or require runtime reflection — but the standards demand a justification comment on every escape hatch.

Recommendation

Add one block comment at the top of the file explaining the pattern, or extract a single typed helper as shown in the Standards section. Either closes the standards gap without introducing structural change.

Singletons (taskDB, searchRateLimiter) couple tests to module load order LowMedium confidenceMedium

src/lib/utils/database.ts (taskDB) · src/lib/utils/security.ts (searchRateLimiter)

Both are module-level singletons. The global mock in src/test/setup.ts defangs taskDB for store tests, and the rate limiter uses an in-memory Map that persists across tests in the same module. This is a low-grade testability concern; it materialises as the store-test isolation issue documented in the Testing section.

Recommendation

Expose factory functions (createTaskDatabase(), createRateLimiter()) alongside the singletons. Tests that need isolation construct their own; production code keeps the singleton. No callers need to change.

Five ADRs covering every hard-to-reverse decision Strength

docs/adr/0001 – 0005

IndexedDB storage, Zustand state management, Next.js static export, Tailwind + shadcn/ui, and dnd-kit are each documented with context, decision, consequences, and alternatives. This is the standards-prescribed pattern and is rare to see fully populated. A new ADR for the IndexedDB migration policy is the natural next addition.

08 — Dimension

Dependencies

0 Critical · 0 High · 1 Medium · 1 Low · 0 vulnerabilities

Dependency hygiene is strong. 28 production packages — small for a stack that includes drag-and-drop, 12 Radix components, a date library, and animation. bun audit reports zero advisories, the lockfile (bun.lock) pins all transitive versions, and overrides in package.json address known issues in brace-expansion, flatted, picomatch, and postcss. All direct dependencies use caret ranges in package.json LowHigh confidenceSmall

package.json — all "^" ranges in dependencies and devDependencies

The standards say "Pin versions in lockfiles. No floating ranges in production." The lockfile pins (bun.lock), so the production install is reproducible. The caret in package.json still permits bun install on a fresh checkout to upgrade across minor versions, which is the supply-chain risk the rule targets — particularly relevant when Claude Code can install packages autonomously.

Recommendation

Either: (a) drop carets to pin exact versions in package.json and rely on a quarterly upgrade cadence with bun outdated, or (b) leave caret ranges but document the policy in CLAUDE.md/coding-standards so the lockfile is authoritative. Option (a) is the standards-aligned choice; option (b) is the pragmatic one.

date-fns imported via barrel rather than per-function subpath LowHigh confidenceSmall

src/lib/utils/taskCardHelpers.tsx:2 — import { format } from 'date-fns'

date-fns v4 is ESM-first and Next.js + Turbopack tree-shake it correctly in this codebase. There is only one import site, so the bundle impact is whatever format's transitive dependencies pull in (locale data is typically the main concern).

Recommendation

Verify with bun run build:analyze that no extra locale data is bundled. If it is, switch to import format from 'date-fns/format'.

Zero advisories, locked versions, version overrides Strength

The overrides block in package.json proactively pins known-problematic transitive dependencies. bun audit returns clean. The Radix primitives are imported as separate packages (each tree-shakeable), and lucide-react exports are centralised in src/lib/icons.ts (a single tree-shake point).

09 — Dimension

Performance

0 Critical · 1 High · 2 Medium · 1 Low

The bundle is well-tuned: 364 KB of JS gzipped across all chunks, with the largest single chunk at 256 KB (uncompressed). 25 dynamic imports drive route- and feature-level code splitting; the drag-and-drop provider is lazy-loaded. Critical render paths (KanbanColumn, TaskCard) are memoized with fast-deep-equal as the comparator. The performance findings concentrate in two areas: notification interval lifecycle and search-cache invalidation.

Notification interval can leak on rapid toggle HighMedium confidenceSmall

src/lib/utils/notifications.ts:91-93 (startPeriodicCheck)

startPeriodicCheck assigns this.checkInterval = setInterval(…) without first clearing an existing interval. If startPeriodicCheck is invoked twice without an intervening stopPeriodicCheck — possible when enableNotifications toggles quickly, or during React Strict Mode double-effects — the old interval is orphaned and continues firing.

Recommendation

startPeriodicCheck(tasks: Task[]) {
  this.stopPeriodicCheck(); // idempotent guard
  this.checkInterval = setInterval(() => this.checkDueTasks(tasks), 5 * 60 * 1000);
  this.checkDueTasks(tasks);
}

Additionally, the tasks closure is captured at call time, so toggling boards keeps notifying about the original task list. Pass tasks via a ref (the pattern is already in KanbanBoard.tsx:79-83 for this exact reason — extend it through to notificationManager).

Search cache may not invalidate on every mutation path MediumMedium confidenceSmall

src/lib/stores/taskStore.filters.ts:~245 (searchCache) · taskStore.crudActions.ts:45 (cache clear on add/update)

The search cache is cleared in the primary mutation paths, but cross-store mutations (e.g. moveTask when board changes, archive operations) may not always reset it. The bug surface is stale search results immediately after a mutation, healing on the next user keystroke.

Recommendation

Centralise cache invalidation: make every mutation in taskStore call a single invalidateSearchCache() helper, or use a derived computed selector that re-runs on dependency change instead of a manual cache. Add a test that asserts cache clears after each mutation type.

Per-task board lookup in render loop MediumHigh confidenceSmall

src/components/kanban/KanbanColumn.tsx:157 — boards.find(b => b.id === task.boardId)

For each rendered task, the component scans the boards array linearly. With 5-10 boards (the realistic upper bound for a personal kanban) and ~100 tasks visible, this is ~1,000 comparisons per render — not a hot-path problem. With cross-board search enabled and the limit pushed higher, this is O(N×M).

Recommendation

Build a Map<boardId, Board> in KanbanBoard (or a derived selector) and pass it in, or call useMemo at the column level. Trivial fix; only worth doing now because the call site is in a memoized component and stable references improve cache hit rate.

Inline style objects in KanbanColumn produce new references per render LowHigh confidenceSmall

src/components/kanban/KanbanColumn.tsx:55-66 (column drop style) and :170 (animationDelay on each task)

The inline-style objects are recreated per render. Children downstream that compare style references will see a change. The column wraps in memo(_, isEqual) with deep equality, so the immediate parent is protected; the children may not be.

Recommendation

Move the conditional drop-zone style into a CSS class toggled by data-isover. Move the staggered animationDelay to a CSS variable on the wrapper. Both convert React reconciliation work into CSS, which the browser handles efficiently.

Bundle within target — 364 KB gzipped total static JS Strength

Total gzipped JS across all static chunks is 364 KB, matching the ~388 KB target documented in CLAUDE.md. Largest single chunk uncompressed is 256 KB. 25 import() sites drive route- and feature-level splitting. next.config.ts uses optimizePackageImports for lucide-react, @radix-ui/react-icons, and @dnd-kit/core.

10 — Dimension

Error handling & observability

0 Critical · 2 High · 1 Medium · 0 Low

Store-level error handling is consistent: every action sets error state on failure, which the UI surfaces via toast. A structured logger exists and is correct (JSON output in production, SSR-safe). Two operational gaps undermine the otherwise solid foundation: no React error boundary, and an init catch that masks failure.

No React error boundary at the application root HighHigh confidenceSmall

src/app/layout.tsx · src/components/KanbanBoard.tsx · grep returned zero ErrorBoundary / componentDidCatch / getDerivedStateFromError matches

Any render error in any component bubbles to React's default behaviour and blanks the UI. The standards list "Frontend interactive elements not keyboard-accessible" and absent error boundaries adjacent in their red-flags taxonomy; React itself documents this as the default-violating case.

Recommendation

// src/components/ErrorBoundary.tsx
'use client';
import { Component, ReactNode } from 'react';
import { logger } from '@/lib/utils/logger';

interface State { error: Error | null; }
export class ErrorBoundary extends Component<{ children: ReactNode; fallback?: ReactNode }, State> {
  state: State = { error: null };
  static getDerivedStateFromError(error: Error) { return { error }; }
  componentDidCatch(error: Error, info: { componentStack?: string | null }) {
    logger.error('Render error', { message: error.message, stack: error.stack, componentStack: info.componentStack });
  }
  render() {
    if (this.state.error) return this.props.fallback ?? <DefaultFallback onReset={() => this.setState({ error: null })} />;
    return this.props.children;
  }
}

Wrap <KanbanBoard> (or the entire app body in layout.tsx) in the boundary. Include a "Try again" button in the fallback that resets the error state, and a "Reset app data" link to resetApp.ts for the catastrophic case.

KanbanBoard.initializeStores swallows errors HighHigh confidenceSmall

src/components/KanbanBoard.tsx:60-66

try {
  await Promise.all([initializeSettings(), initializeBoards(), initializeStore()]);
  setIsInitialized(true);
} catch (error) {
  console.error('Failed to initialize stores:', error);
  setIsInitialized(true); // ← sets initialized even on failure
}

The catch sets isInitialized=true regardless of outcome, so the UI proceeds as if initialization succeeded. Symptoms surface later as cascading failures with no link to root cause — the user sees an empty board with no error message.

Recommendation

const [initError, setInitError] = useState<Error | null>(null);
try {
  await Promise.all([initializeSettings(), initializeBoards(), initializeStore()]);
  setIsInitialized(true);
} catch (error) {
  logger.error('Failed to initialize stores', { error });
  setInitError(error instanceof Error ? error : new Error(String(error)));
}
if (initError) return <InitFailureScreen error={initError} onRetry={() => { setInitError(null); /* re-run effect */ }} />;

Combined with the error boundary above, init failures become recoverable and visible instead of silent.

Logger underused; 31 ad-hoc console.* sites in production code MediumHigh confidenceSmall

src/lib/utils/logger.ts exists (correctly designed) — used in < 5 modules
