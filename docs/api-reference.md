`moveTask` returns `true` only when the status change actually persisted, so callers (e.g. the drag-and-drop handler) can gate side effects like the completion celebration on a real, committed transition instead of firing optimistically.

#### Usage Examples

```typescript
import { useTaskStore } from '@/lib/stores/taskStore';

function TaskComponent({ boardId }: { boardId: string }) {
  const {
    tasks,
    addTask,
    updateTask,
    deleteTask,
    setSearchQuery
  } = useTaskStore();

  // Add a new task — id/createdAt/updatedAt are generated by the store
  const handleAddTask = () => {
    addTask({
      title: 'New Task',
      description: 'Task description',
      status: 'todo',
      priority: 'medium',
      boardId,
      tags: [],
    });
  };

  // Move a task to another status
  const handleUpdateTask = (id: string) => {
    updateTask(id, { status: 'in-progress' });
  };

  // Search tasks (debounced 300ms internally)
  const handleSearch = (query: string) => {
    setSearchQuery(query);
  };
}
```

This app does not have per-board dynamic columns. ## 🧩 Component APIs

### Error Boundary

**Location**: `src/app/error.tsx`

This is a Next.js App Router error boundary, not a reusable React component you import — Next.js automatically renders it when an error is thrown during rendering anywhere under `src/app/`. It follows the framework's `error.tsx` convention:

```typescript
interface ErrorBoundaryProps {
  error: Error & { digest?: string };
  reset: () => void;
}
```

The real implementation only logs `error.message` and `error.digest` via `logger.error` (never the raw `Error` object, since it may reference task/board content the user typed) and renders a "Try again" button (calls `reset()`) alongside a "Reload page" button (`window.location.reload()`). Because this app is 100% client-side/IndexedDB-backed, the copy reassures the user their data is safe in the browser.

### Accessibility Settings

There is no standalone `AccessibilitySettingsDialog` component. Accessibility preferences (`highContrast`, `reduceMotion`, `fontSize`) are fields on `Settings.accessibility` (see [Type Definitions](#type-definitions)) and are edited inline inside `SettingsDialog.tsx` / `SettingsSections.tsx`, alongside theme and other app preferences.

## ⚠️ Error Handling

This app does not have a centralized `AppError`/`ERROR_CODES`/`ErrorRecovery` system. Error handling is deliberately simple and split across two layers:

**Store-level (expected, recoverable errors)**: every async store action wraps its work in `try/catch`. On failure it calls `set({ error: message, isLoading: false })` with a human-readable message (falling back to `'Failed to <verb> <entity>'` when the caught value isn't an `Error`), and most mutating actions also re-throw so the calling UI code can react (e.g. show a toast, keep a dialog open). Example, from `taskStore.crudActions.ts`:

```typescript
export function createAddTask(_get: GetState, set: StoreSetter) {
  return async (taskData: Omit<Task, 'id' | 'createdAt' | 'updatedAt'>) => {
    try {
      set({ isLoading: true, error: null });
      // ...sanitize, persist to taskDB, update state...
    } catch (error: unknown) {
      set({
        error: error instanceof Error ? error.message : 'Failed to add task',
        isLoading: false,
      });
      throw error;
    }
  };
}
```

**App-level (unexpected render errors)**: uncaught errors thrown during rendering are caught by the Next.js App Router error boundary at `src/app/error.tsx` — see [Component APIs](#component-apis). It logs via `logger.error` and offers "Try again" / "Reload page".

**Logging**: `src/lib/utils/logger.ts` exports a `logger` object (`debug`/`info`/`warn`/`error`) used throughout the stores and utilities for structured, leveled logging — plain `console.*` output in development, JSON-line output in production, with `debug` suppressed outside development.

## 🔒 Security APIs

### Input Sanitization

This app does not use DOMPurify. XSS defense is React's automatic escaping of any value rendered as a child or attribute — the `react/no-danger` ESLint rule forbids `dangerouslySetInnerHTML` — backed by the CSP response header. `src/lib/utils/security.ts` adds a defence-in-depth layer on top by stripping raw `<`/`>` characters from user-controlled text before it's written to IndexedDB:

```typescript
import { sanitizeTaskData, sanitizeBoardData } from '@/lib/utils/security';

// Sanitize a task's title/description/tags before persisting
const clean = sanitizeTaskData({
  title: userTitle,
  description: userDescription,
  tags: userTags,
});

// Sanitize a board's name/description before persisting
const cleanBoard = sanitizeBoardData({
  name: userName,
  description: userDescription,
});
```

See `src/lib/utils/security.ts` for the full rationale — earlier revisions also stripped `javascript:`/`data:`/`on\w+=` patterns, but those were removed because they silently corrupted ordinary input (e.g. "metadata: foo" → "meta foo") without preventing any real XSS risk, since none of these values are ever rendered as `href`/`src` or raw HTML.

### Rate Limiting

```typescript
import { searchRateLimiter } from '@/lib/utils/security';

// searchRateLimiter is a pre-configured instance (10 requests / 1s window)
if (searchRateLimiter.isAllowed('search')) {
  // Perform search
} else {
  // Rate limited — the search store action surfaces
  // "Search rate limit exceeded. Please wait a moment before searching again."
}

// Reset a key's request history
searchRateLimiter.reset('search');
```

The `RateLimiter` class itself is not exported — only the shared `searchRateLimiter` instance used by `taskStore.filters.ts` to throttle search-query updates.
