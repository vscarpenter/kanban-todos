1. Standards compliance with coding-standards.md

High   CI tsc --noEmit step fails on test-fixture type drift
Confidence: high src/lib/stores/__tests__/taskStore.import.test.ts:41, 57

Four errors:

TS2322: Type 'Task[]' is not assignable to type 'SerializedTask[]'.
        Types of property 'createdAt' are incompatible.
        Type 'Date' is not assignable to type 'string'.
TS2740: Type '{}' is missing the following properties from type 'Settings':
        theme, autoArchiveDays, enableNotifications, enableKeyboardShortcuts, ...4 more.

The CI workflow (.github/workflows/ci.yml) runs bun run tsc --noEmit as a required step. Vitest does not type-check by default, so unit tests still pass — but CI will block every PR until this is fixed.

Recommendation: serialize the test fixtures to match SerializedTask (ISO date strings) and provide a complete Settings object. Example:

const fixture: SerializedTask = {
  id: 'task-1',
  title: 'Test task',
  status: 'todo',
  boardId: 'board-1',
  priority: 'medium',
  tags: [],
  createdAt: new Date('2024-01-01').toISOString(),
  updatedAt: new Date('2024-01-01').toISOString(),
};

Effort: Small (under 1 day).

High   Three production files exceed the 400-line file limit
Confidence: high src/components/userGuide/guideSteps.tsx (477) · src/components/ExportDialog.tsx (409) · src/components/TaskDialog.tsx (408)

Section §Naming & Clarity in coding-standards.md caps files at "roughly 350 to 400 lines" with "split by responsibility" guidance. The three offending files all sit just over the limit, except guideSteps.tsx which is 19% over.

  • guideSteps.tsx — a single exported array of guide steps with inline JSX content. Splittable into one file per step group (creating, editing, archiving, etc.) or one file per step.
  • ExportDialog.tsx — combines validation state, progress UI, options form, statistics panel, and submit handlers. Extract the export-state hook and the validation/results panel into separate files; keep ExportDialog.tsx as orchestration only.
  • TaskDialog.tsx — same shape as ExportDialog. The useTaskDialogState hook can move out, and the "Show Details" subform can become TaskDialogDetails.tsx.

Recommendation: aim for ≤ 300 lines as a personal target so future additions don't immediately push back over the line.

Effort: Medium (1–5 days for all three).

Medium   Coverage 59.6% / 54.3% sits below the 80% standard
Confidence: high vitest run --coverage

Strong tests where they exist (492 tests, 0 skipped, 0 fail), but several load-bearing files have very thin coverage:

  • src/lib/utils/exportImport.ts — 0% (re-export shim; may be excludable, but currently counted)
  • src/lib/utils/celebrateCompletion.ts — 5%
  • src/lib/stores/taskStore.import.ts — 15%

  • src/lib/utils/conflictResolution.ts — 27% (called by import flow)
  • src/lib/utils/validation.ts — 37% (called by export validation)
  • src/lib/stores/taskStore.ts — 43%

Recommendation: prioritize conflictResolution.ts, validation.ts, and taskStore.import.ts — these are the riskiest paths (data-mutation under conflict). The new e2e suites added in e2e/import-flow.spec.ts and e2e/export-flow.spec.ts already exercise the integration layer; what's missing is unit-level branch coverage.

Effort: Medium.

Medium   Verbose typed-mock pattern increases test brittleness
Confidence: medium src/components/__tests__/BoardView.integration.test.tsx (16+ occurrences)

The pattern (useTaskStore as unknown as ReturnType<typeof vi.fn>).mockReturnValue(...) appears 16+ times in BoardView.integration.test.tsx and similar counts in other integration tests. Total: 71 as unknown casts in the codebase, ~16 of those in production code (mostly cross-board navigation event detail typing).

The tests pass and the typing is sound, but every change to the store's type signature requires editing dozens of mock sites. A typed helper would compress this to one line per test.

Recommendation: introduce a mockStore<T>() helper in src/test/helpers.ts that hides the cast. Migrate opportunistically.

Effort: Small (helper) + Medium (rolling migration).

Low   React act() warnings in KanbanBoard.test.tsx
Confidence: high src/components/__tests__/KanbanBoard.test.tsx

"An update to KanbanBoard inside a test was not wrapped in act(...)" appears 5 times during vitest run. The tests still pass, but the warnings indicate state changes during async store-init are not being awaited.

Recommendation: wrap the initial render in await act(async () => {…}) or use findBy* queries instead of getBy* for the first assertion to await the post-mount update.

Effort: Small.

4. Architecture · coupling, cohesion, layering, SOLID

TL;DR The store layer is well-architected. A composition-layer taskStore.ts aggregates focused sub-modules (crudActions, filters, import). Five ADRs cover load-bearing decisions. The cohesion problems live in components, not in domain logic.
Medium   Two top-level components mix orchestration with presentation
Confidence: high src/components/BoardView.tsx · src/components/KanbanBoard.tsx

BoardView (164 lines) reads from two stores, derives display tasks, groups by board, handles cross-board navigation side-effects, and renders both empty states and three flavours of kanban grid. KanbanBoard.tsx (the top-level wrapper, 119 lines) hosts store initialization, sidebar state, keyboard event listeners, and notification bootstrap.

Recommendation: extract useBoardViewModel hook for the data derivation, a useStoreBootstrap hook for the init effect, and keep the components as thin renderers. This sets up better unit-testability without store-mocking.

Effort: Medium.

Medium   CrossBoardNavigationHandler emits side effects via window events
Confidence: medium src/components/CrossBoardNavigationHandler.tsx

The handler dispatches navigate-to-task-board and board-deleted as custom window events, plus consumes them through addEventListener. Task cards trigger the navigation directly via prop callbacks instead — meaning the toast-emitting code path tied to the custom event is dead in normal user flow. (Confirmed during e2e implementation: clicking a cross-board task card switches the board but does not fire the "Switched to ..." toast.)

Recommendation: either replace the custom-event hop with direct calls to useBoardStore.getState().setCurrentBoard from BoardView (and emit the toast inline), or wire task-card clicks through triggerCrossBoardNavigation so the existing handler runs. The current state advertises a feature that does not work end-to-end.

Effort: Small.

Low   ADR coverage is good but not load-bearing for current decisions
Confidence: medium docs/adr/0001..0005

Five ADRs document the original tech choices (IndexedDB, Zustand, Next.js static export, Tailwind+shadcn, dnd-kit). Newer architectural decisions — modular store split (v3 refactor), Inkwell design tokens adoption, security-headers baseline governance, the CrossBoardNavigationHandler custom-event pattern — are not captured.

Recommendation: add ADRs 0006–0009 covering: store composition pattern, Inkwell adoption, CSP-as-source-of-truth on CloudFront, custom event vs prop drilling for cross-board navigation. The standards (§ADRs) require one when "future engineers will wonder why".

Effort: Small.

8. Error handling and observability

Medium   11 raw console.* calls in production code bypass the structured logger
Confidence: high 11 sites in production code

A structured logger lives at src/lib/utils/logger.ts. It emits JSON log lines in production for log-aggregator ingestion, plain console output in development, and is properly SSR-guarded. The intent is clear, but adoption is partial.

Direct console.error / console.warn sites:

  • src/components/BoardView.tsx:40
  • src/components/InstallPWA.tsx:111
  • src/components/ExportDialog.tsx:161
  • src/components/BoardMenu.tsx:35
  • src/components/KanbanBoard.tsx:63
  • src/components/PwaUpdater.tsx:56, 69, 88
  • src/components/BoardDeleteDialog.tsx:42
  • src/components/SettingsDialog.tsx:135
  • src/components/CrossBoardNavigationHandler.tsx:81

And five direct console.warn calls in src/lib/utils/taskValidation.ts.

The Next.js compiler config has removeConsole: process.env.NODE_ENV === 'production', which strips them in production builds — so log entries are silently dropped in production. That's worse than logging unstructured strings: failures become invisible.

Recommendation:

  1. Migrate all 16 sites to logger.error(...) / logger.warn(...).
  2. Add ESLint rule no-console: ["error", { allow: [] }] with an override for src/lib/utils/logger.ts.
  3. Remove or scope the removeConsole compiler option so the logger output is preserved in production. (The logger uses console.error / console.warn internally, so the strip currently kills production logging.)

Effort: Small (under 1 day).

Medium   No production telemetry or error-tracking integration
Confidence: medium project-wide

The app is privacy-first by design (zero analytics, zero server-side anything), which is correct for the product. But there is also no opt-in error reporting — when a user hits an unhandled promise rejection in production, the team has no signal.

The standards (§Error Handling) call for "Log with context, no secrets" and structured observability. A privacy-respecting option exists: a self-hosted Sentry behind an opt-in flag, or a Service Worker hook that batches structured logs to /api/log only when the user opts in from Settings.

Recommendation: document the deliberate "no telemetry" stance in an ADR (0006-no-default-telemetry.md) so it is a decision rather than an omission. The current tasks/todo.md Tier 3 entry "Add production error tracking recommendation" is already on the backlog.

Effort: Small (ADR), Large (any actual telemetry implementation).

Low   Error boundary coverage is implicit, not enforced
Confidence: medium project-wide

Individual stores expose error state and components render fall-back UI, but there is no top-level React error boundary. A render-time exception in a deep child will currently break the entire app shell. Next.js 16 provides error.tsx for App Router routes, but src/app/page.tsx has no sibling error.tsx.

Recommendation: add src/app/error.tsx with a friendly fallback that offers "Reload" and "Reset application" links (the latter wired to the existing resetApp utility).

Effort: Small.

11. Configuration and type safety

High   Coverage thresholds set well below the standards target (covered in dimensions 1 & 2)
Confidence: high vitest.config.ts:30-33

Repeated here because it lives in config, not in code. See dimension 1.

Medium   removeConsole compiler option silently drops logger output in production
Confidence: high next.config.ts:34

Setting:

compiler: {
  removeConsole: process.env.NODE_ENV === 'production',
},

This strips every console.* call — including the ones inside src/lib/utils/logger.ts — at build time. The structured logger therefore emits nothing in production. If the team intends production observability via structured logs (the logger comments suggest yes), this option is actively defeating that goal.

Recommendation: use the granular form to preserve error and warn:

compiler: {
  removeConsole: process.env.NODE_ENV === 'production'
    ? { exclude: ['error', 'warn'] }
    : false,
},

This pairs with the no-console ESLint rule recommended in dimension 8: developers get a hard error if they introduce console.log; production retains error / warn for the logger.

Effort: Small.

Low   Hardcoded CloudFront distribution IDs in package.json scripts

Methodology and limitations

What was inspected, what was not, and the confidence level you should attach to each class of finding.

What was inspected

  • Static metrics — file and function line counts; console usage; any, non-null assertion, and as unknown usage; TODO/FIXME markers; ESLint suppressions.
  • Tooling output — bun run lint, bun run tsc --noEmit, bun run test, bun run test --coverage, bun audit, bun outdated.
  • Configuration — tsconfig.json, eslint.config.mjs, next.config.ts, vitest.config.ts, playwright.config.ts, sonar-project.properties, .github/workflows/ci.yml, docs/security-headers-baseline.json, react-doctor.config.json.
  • Source code — every file under src/, e2e/, and scripts/ was at least skimmed; load-bearing files (stores, dialogs, security/validation utilities, logger) were read in full.
  • Documentation — README.md, CLAUDE.md, coding-standards.md (v15.0), tasks/todo.md, tasks/lessons.md, five ADRs, the docs/ guides.
  • End-to-end test architecture — 21 spec files; verified the full Playwright suite passes (212 tests) before producing the report.

What was NOT inspected

  • Runtime performance profiling — no Lighthouse, no real-user monitoring, no Chrome DevTools profile capture. Performance findings are derived from code patterns and the documented bundle target, not from runtime measurements.
  • Bundle size analysis — build:analyze exists but was not run as part of this review. The "~388kB" figure in CLAUDE.md is taken on trust.
  • Manual security testing — no penetration test, no fuzz testing of import payloads, no manual XSS attempts beyond the unit-test patterns. The CSP and input-sanitization claims are based on code inspection plus the recurring weekly headers-check workflow.
  • Visual regression — no screenshot diffing. Inkwell-token usage was not verified against rendered output.
  • Production deployment — todos.vinny.dev and cascade.vinny.dev were not curl'd or otherwise probed during this review.
  • License compliance audit — dependency licenses were not enumerated. Spot-checked licenses (Next.js: MIT, React: MIT, Zustand: MIT, lucide-react: ISC, sonner: MIT) are compatible with the project's MIT license, but no exhaustive scan was performed.
  • Accessibility runtime audit — no axe-core run against deployed pages. The accessibility.test.tsx unit tests pass, but full WCAG 2.1 AA conformance was not independently verified.
  • Generated artifacts — out/, .next/, node_modules/, coverage/lcov-report/ were excluded as required.
