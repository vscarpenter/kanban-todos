Kanban-Todos Codebase Analysis Report

Comprehensive code quality review against coding-standards.md v15.0

Repo: kanban-todos Branch: feat/kanban-eve-agent Generated: 2026-07-03 Scope: production src, unit/integration/E2E tests, CI/CD, deploy config

Executive Summary

6.3/10
Solid foundations with several critical, verified defects blocking a higher score. Type safety, security headers, and architecture layering are genuinely strong. But two reliability bugs mean writes can silently fail while the UI reports success, there is no error boundary anywhere in the app, the 4,200-line E2E suite never runs in CI, and multiple developer-facing docs describe an application that doesn't match the real codebase.

Top 5 Risks

  1. Silent write failures. Board/task create, edit, delete, and duplicate actions swallow their own errors — the UI shows a success toast even when the IndexedDB write failed. Critical
  2. No error boundary anywhere. Any uncaught render exception white-screens the entire app; a prior boundary was built, never wired in, then deleted. Critical
  3. E2E suite never runs in CI. 20 spec files / 4,192 lines provide zero regression protection on any PR or merge to main. Critical
  4. Documentation describes a different application. Fabricated APIs (a Board.columns model that doesn't exist), fabricated files/dependencies (DOMPurify, zod, react-router-dom), wrong package manager everywhere. Actively dangerous for onboarding a human or an AI agent. Critical
  5. Raw task content logged to the production console. Task titles/descriptions/tags leak into devtools on validation failures, in a product whose entire value proposition is privacy-first local storage. High

Top 3 Strengths

  1. Strong, verified security posture. Zero XSS sinks, zero hardcoded secrets, strict TypeScript with zero any/@ts-ignore anywhere in src/, and real CSP/HSTS/X-Frame-Options headers confirmed live in production.
  2. Clean, acyclic architecture. UI → store → IndexedDB layering is honored everywhere; no component reaches into the database directly; 524/524 unit tests pass with sensible boundary-level mocking.
  3. Broad, resilient E2E coverage. 20 specs covering CRUD, drag-drop, search, settings, archive, and import/export, built almost entirely on ARIA-role selectors (623 getByRole, zero data-testid) rather than brittle CSS selectors.

Top 3 Priorities — Next Sprint

  1. Fix error-swallowing + add an error boundary. Re-throw after setError in the CRUD store actions and mount a top-level error.tsx. Adjacent code paths, one focused PR. Small–Medium.
  2. Wire the existing E2E suite into CI. The tests already exist and mostly pass (198/217). Adding one CI step converts a large sunk investment into real regression protection. Small.
  3. Redact PII from logging + fix or remove the fabricated docs. Protects end-user privacy and prevents contributors (human or AI) from building against APIs that don't exist. Small–Medium.

Error Handling & Observability (dimension 8)

Findings ▶2 Critical1 High2 Medium2 Low

A split picture. The IndexedDB layer and most store-level catch blocks are solid — nearly every catch calls setError with a real message, and console usage is fully centralized through logger.ts (zero raw console.* calls outside it). The absence of server-side telemetry is a genuine, documented, deliberate privacy tradeoff for this "100% client-side" app — not a gap, and not penalized as one. The two real problems are structural: no error boundary anywhere, and several CRUD actions swallow errors that newer dialog code assumes will propagate.

Methodology & Limitations

What was run

  • bun run test -- --coverage --exclude "**/node_modules/**" --exclude "**/e2e/**" --exclude "**/.agents/**" --exclude "**/.claude/**" --exclude "**/.devin/**" --coverage.reporter=text --coverage.reporter=json-summary --coverage.reporter=lcov — 38 files, 524 tests, all passing. Note: the plain bun run test -- --coverage command as specified in the original brief was run first and returned 1,233 of 1,388 "failed" test files with only 87 real test failures. Investigation showed vitest.config.ts has no include scoping tests to src/, so the default recursive glob picked up ~450 vendored test files under .agents/skills/eve/ (an embedded, unrelated agent framework) — plus duplicates of the same files via .claude/skills/eve and .devin/skills/eve, which are symlinks back to .agents/skills/eve. This is itself a real, reportable config gap (no test-path scoping in vitest.config.ts), separate from and not counted among the findings above since it doesn't affect the shipped app — but it means a naive run of the brief's exact command would have produced a wildly misleading test-health picture. The re-scoped run above is what's reported throughout this document.
  • bun run test:e2e --reporter=json,html (via PLAYWRIGHT_JSON_OUTPUT_NAME) — 217 tests, 198 passed. Note: the first run returned 217/217 "failed," 100% attributable to a single cause: the Chromium binary wasn't installed on this machine (browserType.launch: Executable doesn't exist), not real test failures. bunx playwright install chromium --with-deps was run and the suite re-executed; the 198/19 result above is the genuine, reproducible outcome.
  • bun audit — ran successfully, no fallback needed; 10 advisories captured directly from its output.
  • Direct review (not delegated to an agent): coding-standards.md in full, all 4 GitHub Actions workflows, Dockerfile, deploy scripts/, repo directory structure.
  • Seven parallel read-only research agents, each scoped to 1-2 of the brief's 12 dimensions, instructed to cite file:line evidence for every claim and to mark assumptions/sampling explicitly with lowered confidence. Their raw findings were deduplicated and consolidated into the tables above by a synthesis pass; a small number of near-identical findings from different agents (e.g. the settings-store bypass, found independently by both the architecture and standards agents) were merged into a single row.

Deviations from the original brief

  • The brief assumed E2E specs live at tests/e2e/*.spec.ts with a tests/e2e/pages/ Page Object Model, a tests/e2e/fixtures/ directory, and 3 browser projects (chromium/firefox/webkit). The real repo has specs at ./e2e/*.spec.ts (repository root), no pages/ or fixtures/ directory (confirmed as a real finding, not just a path difference — see TEST-4), and exactly one configured browser project (chromium). This report evaluates the actual structure, not the assumed one.
  • The brief's requested command (bun run test -- --coverage) does not by default produce coverage/coverage-summary.json — vitest.config.ts only configures text/lcov reporters. --coverage.reporter=json-summary was added on the command line (not by editing the config file) to produce it.

What was not inspected

  • No automated cyclomatic/cognitive-complexity tool (e.g. an ESLint complexity plugin) was run. Function-size, nesting-depth, and complexity findings come from agents reading files directly and are sampled, not exhaustive — large directories (especially src/components/) were sampled representatively rather than read file-by-file in full.
  • License findings are based on package.json license-field scanning across installed packages, not a read of each package's actual LICENSE file text — marked Medium confidence for that reason.
  • No full git-blame/history audit was performed beyond targeted git log checks used to date specific claims (e.g. the ADR backfill finding, the REFACTORING-V3.md staleness finding).
  • Firefox and WebKit E2E results are not reported because those browser projects are not configured in this repository's playwright.config.ts — there is nothing to run.
  • No load/stress testing or Lighthouse/Core Web Vitals measurement was performed; performance findings are static-analysis-based (code reading + one build-output inspection for bundle composition), not runtime-profiled.
  • Findings are current as of the commit checked out at report generation time (branch feat/kanban-eve-agent) and will drift as the codebase changes.

Confidence key

Every finding above carries an independent confidence rating from its source agent: High — file:line evidence read directly, no extrapolation. Medium — evidence read directly but the surrounding claim required some inference (e.g. "this pattern likely repeats" without exhaustively checking every instance). Low — evidence is suggestive but incomplete (e.g. a static license-field scan rather than a verified license read). No finding in this report is asserted without at least directly-read evidence backing it.
